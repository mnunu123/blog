## 한 줄 요약

> AI가 그린 상세페이지는 이미지일 뿐이다. 그 위에 진짜 버튼을 얹고, 실제 트래픽으로 A/B를 돌리고, 승자 판단까지 자동화해야 "쓸 수 있는" 페이지가 된다.

---

## 문제

[이전 글](/posts/ai-agent/landing-page-generator-overview)에서 만든 5-에이전트 파이프라인은 13섹션짜리 PNG/PDF를 잘 뽑아낸다. 그런데 이걸 그대로 실제 마케팅 캠페인에 쓸 수는 없었다.

- **클릭이 안 된다**: Gemini가 이미지 안에 "지금 신청하기" 버튼을 그려주긴 하지만, 그건 그림이지 버튼이 아니다.
- **성과를 모른다**: 몇 명이 보고, 몇 명이 눌렀고, 몇 명이 실제로 신청했는지 알 방법이 없다.
- **카피/컬러가 맞는지 확신이 없다**: 에이전트가 만든 헤드라인과 색상 조합이 실제로 더 잘 먹히는지 검증할 방법이 없다.

이 세 가지를 풀지 않으면 "예쁜 이미지 생성기"에서 멈춘다. 실제 상품(OpenClaw라는 퀀트 데이터 API 가상 사전예약, COS 구름백이라는 패션 상품)에 이 프레임워크를 적용해보면서 캠페인으로 굴러가게 만든 과정이다.

---

## 접근 — 이미지는 그대로, 그 위에 인터랙션 레이어를 얹는다

이미지를 다시 HTML로 재조립하는 대신, **PNG는 배경으로 그대로 두고 좌표 기반으로 실제 버튼을 얹는 방식**을 택했다. Gemini가 그린 디자인 품질은 그대로 유지하면서, 인터랙션과 추적만 별도 레이어에서 처리한다.

```
cf-pages/
  index.html        # 이미지 로드 + 버튼 렌더링 + GA4 + Formspree 모달
  cta_slots.json     # 버튼 좌표(%), 마스크 좌표, variant별 색상, GA4 파라미터
  images/
    final_page_A.png
    final_page_B.png
```

`cta_slots.json`에 버튼 위치를 퍼센트 좌표로 저장해두면, 화면 크기가 달라져도(`width: 100%`인 이미지 위에 `%` 좌표로 버튼을 겹치므로) 버튼이 항상 이미지의 정확한 위치에 붙는다.

![Gemini로 생성한 OpenClaw 상세페이지 — Hero부터 Before/After 섹션까지](/images/landing-page-generator/final-page-a-full.png)

*그림 1: 5-에이전트 파이프라인이 생성한 실제 상세페이지(A 변형). 이 위에 진짜 버튼을 얹는다.*

## 구현

### 1. CTA 마스킹 — Gemini가 그린 가짜 버튼 잔상 지우기

Gemini에게 "버튼이 있는 히어로 섹션"을 그려달라고 하면, 실제로 버튼처럼 생긴 도형을 그림 안에 그려 넣는다. 이 가짜 버튼 위에 진짜 버튼을 얹으면 살짝 어긋나 보이거나 이중으로 보인다. 그래서 진짜 버튼 뒤에 반투명 마스크를 먼저 깔아서 원본 잔상을 지운다.

```javascript
// cf-pages/index.html
// 배경 마스크: Gemini가 그린 반투명 사각형/잔상을 덮어 숨김
.cta-mask {
  position: absolute;
  background: rgba(10, 15, 30, 0.82);
  backdrop-filter: blur(10px);
  border-radius: 16px;
}
```

`cta_slots.json`에서 버튼(`slots[].left_pct/top_pct/width_pct`)과 마스크(`slots[].mask`) 좌표를 각각 따로 관리해서, 마스크가 버튼보다 살짝 크게 깔리도록 조정했다.

### 2. A/B 변형 배정 — URL 파라미터 > localStorage > 쿠키 > 랜덤

```javascript
// 우선순위: URL ?var= > localStorage > cookie > 랜덤 신규
function resolveVariant() {
  var p = new URLSearchParams(location.search).get('var');
  if (p === 'A' || p === 'B') { persistVariant(p); return p; }

  var s = localStorage.getItem(CONFIG.STORAGE_KEY) || getCookie(CONFIG.STORAGE_KEY);
  if (s === 'A' || s === 'B') return s;

  var v = Math.random() < 0.5 ? 'A' : 'B';
  persistVariant(v);
  return v;
}
```

`?var=A`로 직접 지정할 수 있게 해둔 게 실제로 유용했다 — 디자이너/기획 검토용 링크를 보낼 때 매번 새로고침해서 랜덤 배정을 기다릴 필요가 없다. 한 번 배정된 variant는 30일 쿠키 + localStorage에 저장해서, 같은 사용자가 재방문해도 같은 버전을 본다.

### 3. GA4 이벤트 3종 + Formspree 신청 폼

퍼널을 3단계 이벤트로 나눴다: `lp_impression`(페이지 로드) → `lp_cta_click`(버튼 클릭, 모달 오픈) → `lp_reserve_submit`(신청 폼 제출 성공). 모든 이벤트에 `exp_id`/`var`/`page_id`를 공통으로 실어서 나중에 변형별로 쪼개 볼 수 있게 했다.

```javascript
function sendGA4(eventName, extra) {
  var params = Object.assign(
    { exp_id: CONFIG.EXP_ID, var: VARIANT, page_id: CONFIG.PAGE_ID },
    extra || {}
  );
  if (typeof gtag === 'function') gtag('event', eventName, params);
}
```

신청 폼은 Formspree로 보내되, `fetch`로 비동기 제출해서 페이지 이동 없이 모달 안에서 성공 화면을 보여준다. `hasSubmitted` 플래그로 중복 제출을 막고, `lp_reserve_submit`은 Formspree가 200을 반환한 뒤 딱 한 번만 발사되도록 했다.

### 4. `run_ab.py` — A/B 두 버전을 한 번에 생성하고 타임스탬프로 보관

```python
# scripts/run_ab.py
# python scripts/run_ab.py                          → A, B 둘 다 새로 생성
# python scripts/run_ab.py --use-run 20260228_1430  → 과거 결과를 cf-pages에 복사
```

OpenClaw 실험에서는 같은 상품을 컬러/카피 톤만 다르게 두 버전 만들었다 — A는 시안 컬러 + 가격 절감 강조, B는 네온 그린 + "전처리 제로" 강조. 생성할 때마다 `output/runs/{timestamp}/A`, `.../B`에 각각 저장해두고, 마음에 드는 실행 결과만 골라서 `cf-pages/images/`로 복사하는 구조라 재생성 없이 과거 결과를 재사용할 수 있다.

### 5. GA4 지표 자동 수집 + 요약

```python
# tools/ga4_pull.py — 최근 7일 lp_impression/lp_cta_click/lp_reserve_submit을 GA4 Data API로 가져온다
# rich 모드(커스텀 디멘션 포함) 시도 → 실패하면 basic 모드로 자동 폴백
mode = "rich"
try:
    result = run_report(client, property_id, RICH_DIMENSIONS, hostname)
except Exception as e:
    if is_dim_err:
        mode = "basic"
        result = run_report(client, property_id, BASIC_DIMENSIONS, hostname)
```

`ga4_summarize.py`가 이 원본 이벤트를 variant별/CTA별/섹션별 CTR·CVR·Submit Rate 표로 집계해서 `metrics_summary.md`로 뽑는다.

### 6. `ab_decide.py` — 통계적 기준을 통과해야만 승자를 선언한다

가장 신경 쓴 부분이다. "A가 더 높으니까 A 승리"라고 바로 판단하지 않는다.

```python
THRESHOLDS = {
    "min_submits_total":    10,    # 전체 제출 10건 미만이면 판단 보류
    "min_impressions_each": 100,   # variant당 노출 100 미만이면 판단 보류
    "max_imbalance":        0.20,  # 노출 배정이 20% 이상 치우치면(SRM) 판단 보류
    "min_cvr_delta":        0.002, # CVR 차이가 0.2%p 미만이면 "동률"로 처리
}
```

`max_imbalance`는 SRM(Sample Ratio Mismatch) 체크다 — A/B가 50:50으로 배정됐어야 하는데 실제 노출이 한쪽으로 크게 쏠려 있으면, 배정 로직 자체에 버그가 있다는 신호이므로 결과를 믿지 않고 판단을 보류한다. 이 조건들을 모두 통과해야 `declare_winner` 상태가 되고, 하나라도 못 미치면 `collect_more`(표본 더 모으기) 또는 `hold`(동률)로 응답한다.

## 시행착오

### 실제 트래픽은 아직 판단 기준에 한참 못 미친다

Cloudflare Pages에 실제로 배포하고 GA4로 이벤트를 받아보긴 했다. 하지만 실제 수집된 지표는 이랬다.

```json
// metrics/ga4_20260303_051844_basic.json (발췌)
{ "date": "20260302", "eventName": "lp_impression", "eventCount": "4" },
{ "date": "20260302", "eventName": "lp_cta_click",   "eventCount": "2" }
```

노출 4건, 클릭 2건. `ab_decide.py`의 최소 조건(variant당 노출 100건, 전체 제출 10건)에는 한참 못 미치는 숫자다. 즉 이 프로젝트에서 실제로 검증한 건 "A와 B 중 뭐가 더 잘 팔리는가"가 아니라 **"추적·집계·판단 파이프라인이 실제 배포 환경에서 끊기지 않고 동작하는가"** 쪽이다. 통계적으로 유의미한 승자 판단은 실제 트래픽이 충분히 모여야 나온다 — 지금은 그 앞 단계까지 만들어 둔 상태다.

### GitHub Actions로 자동화하려던 계획은 레포에서 제외했다

`ga4_pull.py`는 원래 GitHub Actions cron으로 매일 자동 실행할 계획으로 만든 스크립트다. 커밋 로그에도 `cron schedule to daily UTC 02:00`, `remove git push from GA4 workflow to prevent push conflicts` 같은 흔적이 남아있다. 하지만 최종적으로 `.github/workflows`는 레포 권한 스코프 문제로 제외했다(`Exclude workflow files (no workflow scope)`) — 지금은 로컬에서 수동으로 돌리는 상태고, 워크플로 파일 자체는 다음에 권한을 다시 잡을 때 되살릴 항목으로 남겨뒀다.

## 결과

- 정적 PNG 위에 좌표 기반 CTA 버튼 + 마스크를 얹어 실제로 클릭 가능한 페이지로 전환
- A/B 두 변형을 같은 파이프라인으로 생성 → Cloudflare Pages(`cf-pages/`)로 배포
- GA4 이벤트 3종(노출/클릭/신청) 수집 → 변형별 자동 집계 → 통계 기준 승자 판단까지 코드로 연결
- 같은 프레임워크를 다른 브리프(COS 구름백 — 패션 상품)에도 그대로 적용해 재사용 가능함을 확인
